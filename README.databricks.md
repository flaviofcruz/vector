134. Fix read-side `delivery_method` inference in `DeliveryReadEvent::emit`. `deliveryMethod` denotes *how the content was read* — `VECTOR_WOODCHUCK_V2_FILE` (read from files) vs `VECTOR_WOODCHUCK_V2_DISKLESS` (diskless gRPC) — not the topic type. The previous `SOURCE_TYPE_KUBERNETES_LOGS → VECTOR_WOODCHUCK_V2_KUBERNETES_LOGS` mapping was wrong: the Databricks fork's `kubernetes_logs` source reads Lumberjack proto files (and pod stdout) from container directories, and downstream VRL stamps those events `logMetadata.deliveryMethod=VECTOR_WOODCHUCK_V2_FILE` — so the read side reported `KUBERNETES_LOGS` while the sink reported `FILE`, and a `delivery_method="VECTOR_WOODCHUCK_V2_FILE"` SLI filter returned zero reads. The read counter only fires for the `file` and `kubernetes_logs` sources (both read from files); the diskless gRPC source emits no read event. `delivery_method_for_source_type` now maps both file-reading sources to `VECTOR_WOODCHUCK_V2_FILE`, so the read-side label is always file-based and consistent with the file-based VRL stamping. There is no `VECTOR_WOODCHUCK_V2_KUBERNETES_LOGS` delivery method (it is not in the `VectorDeliveryMethod` proto enum); sawmill stays distinguishable via the `topic` label (`sawmill-service-log`).
135. Correct the config-reload VEL service events so a reload success/failure rate is computable from the Vector Event Log. PR #532 emitted `service_event = 6` from `VectorConfigLoadError` (a failure), but `6 = VECTOR_CONFIG_RELOAD_SUCCESS` in the `VectorServiceEventType` proto enum (`7 = VECTOR_CONFIG_RELOAD_FAILURE`) — so every reload failure was logged as a SUCCESS and no FAILURE event was ever emitted. This change: (a) emits `VECTOR_CONFIG_RELOAD_SUCCESS` (6) from `VectorReloaded`, the real success path, which previously emitted no service event (so there was no denominator); (b) fixes `VectorConfigLoadError` to emit `VECTOR_CONFIG_RELOAD_FAILURE` (7); (c) emits `VECTOR_CONFIG_RELOAD_FAILURE` (7) from `VectorReloadError` ("Reload was not successful"), also a per-attempt reload failure. `VectorRecoveryError` intentionally emits no VEL event — it is a follow-on to an already-counted failed reload and would double-count. Reload events are mutually exclusive per attempt, so `failure_rate = FAILURE / (SUCCESS + FAILURE)` per shard/region is well-defined. Amends https://github.com/databricks-eng/vector/pull/532

Add an opt-in path for `kubernetes_logs::util::run_file_server` to run `FileServer::run` directly on the surrounding async runtime instead of inside the legacy `tokio::task::spawn_blocking` + `tokio::runtime::Handle::block_on` wrapper, gated on a new default-off global config flag `async_kubernetes_logs_file_server` (mirroring `two_wave_shutdown` in `lib/vector-core/src/config/global_options.rs`).
